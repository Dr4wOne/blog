<Aside title="In short">

People write programs as text. A processor only understands long lists of tiny numbered instructions. A compiler is the program that translates one into the other, in a fixed order of steps: it splits the text into words, works out the grammar, checks that it makes sense, rewrites it into a simpler in-between form, improves it, and finally writes instructions. Go does all of this before the program ever runs. Java and Python stop halfway, at a form called bytecode, and bring a helper program that runs it. Every example here was run on my laptop, and the outputs are real. A short glossary sits at the end, in the [recap](#recap).

</Aside>

You use compiled programs all day: your browser, your phone's apps, the software in your car. Almost all of their code was written in a language the machine cannot run. This post explains, from zero, what happens in between. You do not need to have written a line of code.

## What code is

Code, or **source code**, is a set of instructions for a computer, written by a person as plain text in a programming language. A programming language is a small, strict language with exact rules for spelling and grammar, much stricter than English.

Here is a complete program in Go, one of the three languages in this post. It works out a price with tax, in cents: 200 cents plus 10 percent.

```go
package main

import "fmt"

func total(price, rate int) int {
	return price + price*rate/100
}

func main() {
	fmt.Println(total(200, 10))
}
```

`func total` defines a **function**: a named, reusable recipe that takes inputs (`price` and `rate`) and gives back a result. `int` means a whole number. `*` means multiply, `/` means divide, and `return` hands the result back. `main` is where the program starts, and `fmt.Println` prints the answer on the screen: `220`. The first two lines say "this is a program" and "I will use the printing toolbox, `fmt`".

A person can read this. A processor cannot.

## Why the computer can't read it

The **processor** (or CPU) is the chip that does the work. It understands one thing only: **machine code**, a list of very small instructions, each stored as a few bytes (numbers from 0 to 255). Each instruction does almost nothing: copy a number into one of the chip's few storage slots, multiply two slots, jump to another instruction. Different families of processors, such as the Intel chip in my laptop and the ARM chip in a phone, understand different instructions.

So the word `price` means nothing to the chip. Neither does `+`, or the idea of a function. Someone has to translate.

> **Analogy:** think of a cook who only understands a handful of short commands in their own language: "take", "add", "stir", "go to step 4". You wrote a recipe in English, with full sentences. Before the cook can start, somebody must translate the recipe into those commands. That somebody is a compiler.

A **compiler** is a program that translates source code into a form a machine can run, and it does so before the program runs. The idea is old. In 1957 IBM released FORTRAN, the "Formula Translating System", so that scientists could type formulas and let the machine turn them into machine code.[^fortran]

**In one line:** people write text, chips run numbers, and a compiler translates between them.

## The compiler's steps

Every compiler, big or small, does roughly the same steps in the same order. The textbook on the subject, known as the Dragon Book, lists them,[^dragon] and the Go compiler's own documentation names the same ones.[^gocompile] Follow one line through them: `price + price*rate/100`.

<CompilerStages />

**1. Splitting into tokens.** At first the compiler sees only characters: `p`, `r`, `i`, `c`, `e`, a space, `+`. The first step, called **lexing**, groups them into **tokens**, the words of the language. Python comes with a tool that shows this step.[^tokenize] Here is the Python version of our line, saved in a file called `line.py`:

```python
total = price + price * rate // 100
```

(Python writes whole-number division as `//`; Java and Go write `/`.) The tool prints one token per row. The numbers on the left are positions: `1,0-1,5` means line 1, from character 0 to character 5.

```text
$ python3 -m tokenize line.py
1,0-1,5:   NAME     'total'
1,6-1,7:   OP       '='
1,8-1,13:  NAME     'price'
1,14-1,15: OP       '+'
…
1,29-1,31: OP       '//'
1,32-1,35: NUMBER   '100'
```

The full output (trimmed here) has nine tokens: four names (`total`, `price`, `price`, `rate`), four operators (`=`, `+`, `*`, `//`) and one number. Spaces are gone; they only separate words.

**2. Building a tree.** Next comes **parsing**: arranging the tokens into a **syntax tree**, a diagram of what belongs to what, like the grammar diagrams some of us drew at school. The tree decides the order. Multiplication and division come before addition, so `price*rate` is grouped first, then divided by 100, then added to `price`.[^ast]

<Aside title="Deep dive: Python's tree for this line">

Python prints its tree with `ast.dump`. Read it from the inside out: multiply, then divide, then add. `BinOp` means "an operation with two sides".

```text
BinOp(
  left=Name(id='price', ctx=Load()),
  op=Add(),
  right=BinOp(
    left=BinOp(
      left=Name(id='price', ctx=Load()),
      op=Mult(),
      right=Name(id='rate', ctx=Load())),
    op=FloorDiv(),
    right=Constant(value=100)))
```

</Aside>

**3. Checking the meaning.** A sentence can be grammatical and still make no sense: "the price ate the tax". Here the compiler checks things like **types**, the kind of value each name holds. `price` and `rate` are whole numbers, so multiplying them is allowed and the result is a whole number. In Go or Java, passing a word where a number belongs is refused with an error message, and nothing is built. Go calls this step type checking.[^gocompile]

**4. An in-between form.** The tree is now rewritten into a simpler language the compiler uses only for itself, called an **intermediate representation**, or IR. It looks like a list of tiny steps, each with a numbered scratch value: first `t1 = price * rate`, then `t2 = t1 / 100`, then `t3 = price + t2`. Go's version is called SSA (static single assignment), where each scratch value is written exactly once.[^gocompile] This form is far easier to improve and to translate than the original text.

**5. Optimizing.** **Optimizing** means rewriting the steps so the program runs faster or smaller, without changing what it does. A small example from my Go program: dividing is slow for a processor, so the Go compiler replaced "divide by 100" with a multiplication by a large, carefully chosen number, followed by a "shift" (a cheap instruction that moves the digits of a number, like dividing by ten by dropping the last digit). It gives the same answer, faster.[^granlund] Another: it saw that `total(200, 10)` always gives 220 and wrote the number 220 straight into the program.

**6. Generating code.** Finally, **code generation** turns the in-between form into instructions for one kind of processor, or into bytecode, which the next section explains. For my laptop's Intel chip, Go turned the function `total` into 12 machine instructions, 45 bytes in all.

**In one line:** words, then grammar, then meaning, then a simple plan, then a better plan, then instructions.

## Three ways to run code

Not every language runs all six steps before you press "go". There are three common routes.

**Ahead of time.** The compiler runs all the steps once, on the programmer's computer, and produces a file of machine code. You run that file; the compiler is not needed any more. This is **ahead-of-time** (AOT) compilation. Go works this way. In the cookbook picture, the whole book is translated before the cook opens it.

**Interpreting.** An **interpreter** is a program that reads instructions and carries them out one at a time, while the program runs, without producing a machine-code file. It is a translator who stands next to the cook and reads each line aloud as the cooking happens. It needs no separate build step and is flexible, but the translating never stops, so programs generally run more slowly.[^pyglossary]

**Bytecode and a virtual machine.** Many popular languages mix the two. A compiler does the first steps and writes **bytecode**: instructions for an imaginary, simplified processor, designed so that any real computer can run them. A program called a **virtual machine** (VM) then runs that bytecode on the real chip. In the kitchen, the recipe is written in a shorthand that every local helper can read.

**Just in time.** Java's VM goes one step further. At first it interprets the bytecode, one instruction at a time, just like Python. Meanwhile it watches which parts run most often, the "hot" parts, and compiles those into real machine code while the program is running. That is called **just-in-time** (JIT) compilation.[^javaman] The helper notices the same sauce being made every day and writes out a full translation of that one page.

**In one line:** translate everything first, translate as you go, or translate halfway and finish on each machine.

## The same program three ways

Here is the price-with-tax program in all three languages, built and run on one laptop with Java 25 (the OpenJDK edition), Python 3.10 and Go 1.27. Each one prints `220`. Lines that start with `$` are commands I typed.

### Java: bytecode, then a virtual machine

```java
public class Tax {
    static int total(int price, int rate) {
        return price + price * rate / 100;
    }

    public static void main(String[] args) {
        System.out.println(total(200, 10));
    }
}
```

Java needs a little more ceremony: everything lives inside a `class`, and `System.out.println` prints. `javac Tax.java` compiles it into `Tax.class`, a file of Java bytecode, 456 bytes long.[^javac] The command `javap -c` shows what is inside, in readable form (trimmed to the `total` function):[^javap]

```text
$ javap -c Tax.class
  static int total(int, int);
    Code:
       0: iload_0
       1: iload_0
       2: iload_1
       3: imul
       4: bipush        100
       6: idiv
       7: iadd
       8: ireturn
```

Eight instructions. `iload` puts a number on a pile (a "stack"), `bipush 100` puts the number 100 there, `imul` multiplies the top two, `idiv` divides, `iadd` adds, `ireturn` hands back the answer.[^jvms6] Notice that this is still not Intel or ARM code. The Java specification says it plainly: the Java Virtual Machine "knows nothing of the Java programming language, only of a particular binary format, the class file format".[^jvms1] The same `Tax.class` runs on any computer that has a Java VM.

To watch the JIT at work, I called `total` a million times in a loop. Java compiled it twice: first a quick version, then, because it stayed busy, a better one.[^tiered]

<Aside title="Deep dive: the JIT log">

`-XX:+PrintCompilation` prints a line each time a method is compiled.[^javaman] I kept only the `TaxLoop` lines. The third number is the level: 3 is the quick compiler with profiling, 4 the fully optimizing one.[^tiers] "9 bytes" is the size of `total`'s bytecode.

```text
$ java -XX:+PrintCompilation TaxLoop | grep TaxLoop::
13    8       3       TaxLoop::total (9 bytes)
13    9       4       TaxLoop::total (9 bytes)
…
```

</Aside>

### Python: bytecode, then an interpreter

```python
def total(price, rate):
    return price + price * rate // 100

print(total(200, 10))
```

`def` defines the function, and `print` prints. Python is often called "interpreted", but it compiles too. The official glossary says so: "Python source code is compiled into bytecode", and that bytecode can be cached (saved for reuse) in `.pyc` files so the next start is faster.[^pyglossary] Compiled with `python3 -m py_compile`, the cached `.pyc` file for this program is 254 bytes. The `dis` tool shows the bytecode of `total`:[^dis]

```text
  2   0 LOAD_FAST        0 (price)
      2 LOAD_FAST        0 (price)
      4 LOAD_FAST        1 (rate)
      6 BINARY_MULTIPLY
      8 LOAD_CONST       1 (100)
     10 BINARY_FLOOR_DIVIDE
     12 BINARY_ADD
     14 RETURN_VALUE
```

Eight instructions again, and almost the same ones as Java: load, load, load, multiply, load 100, divide, add, return. The difference is what happens next. In Python 3.10 the interpreter carries out these instructions one by one, every time, and never turns them into machine code. Python 3.13 added an experimental JIT, switched off unless Python is built with it.[^pep744]

### Go: machine code, ahead of time

```text
$ go build -o tax tax.go
$ ls -l tax
… 2346857 out 26 23:29 tax
$ file tax
tax: ELF 64-bit LSB executable, x86-64, … statically linked, …
$ ./tax
220
```

`go build` runs every step at once and writes `tax`, a file of real machine code.[^gobuild] `ls -l` shows its size in bytes, `file` describes it, and `./tax` runs it.

That file is called an **executable**, or a **binary**: a program ready to start. It contains machine code for one family of chips, here x86-64, the family of Intel and AMD processors. It is packed in the file format that one operating system knows how to start: ELF on Linux, with different formats on Windows and macOS. So the same file will not run on a phone's ARM chip or on Windows. Go can build a separate binary for each, chosen with two settings: `GOOS` for the operating system and `GOARCH` for the chip.[^goenv]

It is 2.3 MB for a program that prints one number, because Go copies everything the program needs into that one file, including the Go runtime, its built-in helper code, plus type and debugging information. Go's documentation calls this "statically-linked".[^gofaq] The good side: you can copy that single file to another Linux computer with the same kind of chip and run it, with nothing else installed.

The Go compiler can also print the machine code it wrote. It confirms both tricks from step 5: the division became a multiply and a shift, and the compiler did the sum while building, so the finished program simply contains the answer, 220.[^gocmd]

<Aside title="Deep dive: Go's machine code">

From `go build -a -gcflags=-S` (directives, addresses and file names trimmed). The giant number replaces "divide by 100"; `SARQ` is the shift. In `main`, the call to `total` is gone: the compiler copied the function into place ("inlining") and worked out the result, so the code just says `MOVL $220, AX`, "put 220 in a slot".

```text
main.total STEXT nosplit size=45 …
  IMULQ  AX, BX
  …
  MOVQ   $-6640827866535438581, AX
  …
  SARQ   $6, CX
  SUBQ   BX, CX
  LEAQ   (CX)(SI*1), AX
  RET
```

</Aside>

**In one line:** Java and Python both make bytecode; Java's VM compiles the busy parts at run time, Python 3.10 interprets, and Go hands over a finished binary.

## Errors: caught early or caught late

The meaning check in step 3 is where many mistakes are caught. I made the same mistake in all three programs: passing the price as text, `"200"` (in quotes), instead of the number 200. Programmers call a piece of text a "string".

Java and Go refuse to build at all (output trimmed):[^jls][^gospec]

```text
$ javac Tax.java
Tax.java:7: error: incompatible types: String cannot be converted to int
$ go build -o tax tax.go
./tax.go:10:20: cannot use "200" (untyped string constant) as int value in argument to total
```

No program file is produced, so the mistake cannot reach anyone. Python checks types only when a line actually runs. My broken Python program printed "Starting..." first, and failed only when it reached the bad line. A "traceback" is Python's report of where it was when it failed:

```text
Starting...
Traceback (most recent call last):
  …
TypeError: unsupported operand type(s) for //: 'str' and 'int'
```

Neither approach is simply better. Checking early catches whole families of mistakes before a program reaches you. Checking late lets programmers try ideas quickly, without writing out every type. But if you have ever seen an app crash on one particular screen, you have met an error that nothing caught early.

**In one line:** a compiler that checks types turns some crashes into error messages for the programmer instead.

## Why it matters to you

You will probably never run a compiler. Its work still shows up in your day.

- **Speed.** Optimized machine code does the same work with fewer, cheaper instructions, like the division trick above. The JIT is why a long-running Java program speeds up after it starts.[^tiered]
- **Errors caught early.** Every mistake a compiler refuses is one that never reaches your screen.
- **One program, many machines.** Bytecode lets one Java file run on any computer that has a Java VM, whatever its chip.[^jvms1] Go goes the other way and builds one binary per kind of computer.[^goenv]
- **Memory.** Bringing a helper costs something. On my laptop, at their peak, the tiny Java program used about 42 MB of memory, the Python one about 9 MB, and the Go one about 2 MB. The VM and the interpreter come along for the ride.

And like a compiler, it must give exactly the same result for the same input, or none of that reuse would be safe.

## Recap

- Source code is text written by people; a processor only runs machine code, tiny numbered instructions.
- A compiler translates in fixed steps: tokens, tree, meaning check, in-between form, optimizing, code generation.
- Go compiles ahead of time into one binary, for one kind of chip and one operating system.
- Java compiles to bytecode; its virtual machine interprets it, then compiles the busy parts to machine code (JIT).
- Python compiles to bytecode too, and in version 3.10 interprets it one instruction at a time.
- Compilers that check types turn some crashes into error messages before you ever see the program.
- The same ideas work outside programming: check the input early, rebuild only what changed, and keep the output repeatable.

| Word | Meaning |
| --- | --- |
| Source code | Instructions written by a person as text |
| Machine code | Instructions a processor runs directly |
| Binary, executable | A file of machine code for one kind of chip and one operating system |
| Compiler | A program that translates source code before it runs |
| Interpreter | A program that carries out instructions one at a time while the program runs |
| Bytecode | Instructions for an imaginary processor, run by a virtual machine |
| JIT | Compiling the busy parts to machine code while the program runs |
| Type | The kind of value a name holds, such as a whole number or text |
