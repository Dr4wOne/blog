<Aside title="In short">

People write programs as text. A processor only understands long lists of tiny numbered instructions. A compiler is the program that translates one into the other, in a fixed order of steps: it splits the text into words, works out the grammar, checks that it makes sense, rewrites it into a simpler in-between form, improves it, and finally writes instructions. Go does all of this before the program ever runs. Java and Python stop halfway, at a form called bytecode, and bring a helper program that runs it. Every example here was run on my laptop, and the outputs are real.

</Aside>

You use compiled programs all day: your browser, your phone's apps, the software in your car. None of them were written in the language the machine runs. This post explains, from zero, what happens in between. You do not need to have written a line of code.

## What code is

Code, or **source code**, is a set of instructions for a computer, written by a person as plain text in a programming language. A programming language is a small, strict language with exact rules for spelling and grammar, much stricter than English.

Here is a complete program in Go, one of the three languages in this post. It works out a price with tax, in cents: 200 cents plus 10 percent.

```go
func total(price, rate int) int {
	return price + price*rate/100
}

func main() {
	fmt.Println(total(200, 10))
}
```

`total` is a **function**: a named, reusable recipe that takes inputs (`price` and `rate`) and gives back a result. `int` means a whole number. `main` is where the program starts, and `fmt.Println` prints the answer on the screen: `220`.

A person can read this. A processor cannot.

## Why the computer can't read it

The **processor** (or CPU) is the chip that does the work. It understands one thing only: **machine code**, a list of very small instructions, each stored as a few bytes (numbers from 0 to 255). Each instruction does almost nothing: copy a number into a slot, multiply two slots, jump to another instruction. Different families of processors, such as the Intel chip in my laptop and the ARM chip in a phone, understand different instructions.

So the word `price` means nothing to the chip. Neither does `+`, or the idea of a function. Someone has to translate.

> **Analogy:** think of a cook who only understands a handful of short commands in their own language: "take", "add", "stir", "go to step 4". You wrote a recipe in English, with full sentences. Before the cook can start, somebody must translate the recipe into those commands. That somebody is a compiler.

A **compiler** is a program that translates source code into a form a machine can run, and it does so before the program runs. The idea is old. In 1957 IBM released FORTRAN, the "Formula Translating System", so that scientists could type formulas and let the machine turn them into machine code.[^fortran]

**In one line:** people write text, chips run numbers, and a compiler translates between them.

## The compiler's steps

Every compiler, big or small, does roughly the same steps in the same order. The textbook on the subject, known as the Dragon Book, lists them,[^dragon] and the Go compiler's own documentation names the same ones.[^gocompile] Follow one line through them: `price + price*rate/100`.

<CompilerStages />

**1. Splitting into tokens.** At first the compiler sees only characters: `p`, `r`, `i`, `c`, `e`, a space, `+`. The first step, called **lexing**, groups them into **tokens**, the words of the language. Python comes with a tool that shows this step.[^tokenize] For the Python version of the line, it prints (trimmed):

```text
$ python3 -m tokenize line.py
1,0-1,5:   NAME     'total'
1,6-1,7:   OP       '='
1,8-1,13:  NAME     'price'
1,14-1,15: OP       '+'
…
1,29-1,31: OP       '//'
1,32-1,35: NUMBER   '100'
```

Nine tokens: four names, four operators and one number. Spaces are gone; they only separate words. (Python writes whole-number division as `//`; Java and Go write `/`.)

**2. Building a tree.** Next comes **parsing**: arranging the tokens into a **syntax tree**, a diagram of what belongs to what, like the grammar diagrams some of us drew at school. The tree decides the order. Multiplication and division come before addition, so `price*rate` is grouped first, then divided by 100, then added to `price`. Python can show its tree too:[^ast]

```text
BinOp(
  left=Name(id='price', ctx=Load()),
  op=Add(),
  right=BinOp(
    left=BinOp(
      left=Name(id='price', ctx=Load()),
      op=Mult(),
      right=Name(id='rate', ctx=Load())),
    op=FloorDiv(),
    right=Constant(value=100)))
```

`BinOp` means "an operation with two sides", and `ctx=Load()` means "read this value". Read it from the inside out: multiply, then divide, then add.

**3. Checking the meaning.** A sentence can be grammatical and still make no sense: "the price ate the tax". Here the compiler checks things like **types**, the kind of value each name holds. `price` and `rate` are whole numbers, so multiplying them is allowed and the result is a whole number. Trying to multiply a word by a number is refused, with an error message, and nothing is built. Go calls this step type checking.[^gocompile]

**4. An in-between form.** The tree is now rewritten into a simpler language the compiler uses only for itself, called an **intermediate representation**, or IR. It looks like a list of tiny steps, each with a numbered scratch value: first `t1 = price * rate`, then `t2 = t1 / 100`, then `t3 = price + t2`. Go uses a form called SSA, where each scratch value is written exactly once.[^gocompile] This form is far easier to improve and to translate than the original text.

**5. Optimizing.** **Optimizing** means rewriting the steps so the program runs faster or smaller, without changing what it does. A small example from my Go program: dividing is slow for a processor, so the Go compiler replaced "divide by 100" with a multiplication by a large, carefully chosen number followed by a shift, which gives the same answer faster.[^granlund] Another: it saw that `total(200, 10)` always gives 220 and wrote the number 220 straight into the program. More on that below.

**6. Generating code.** Finally, **code generation** turns the in-between form into instructions for one kind of processor, or into bytecode, which the next section explains. For my laptop's Intel chip, Go turned the function `total` into 12 machine instructions, 45 bytes in all.

**In one line:** words, then grammar, then meaning, then a simple plan, then a better plan, then instructions.

## Three ways to run code

Not every language runs all six steps before you press "go". There are three common routes.

**Ahead of time.** The compiler runs all the steps once, on the programmer's computer, and produces a file of machine code. You run that file; the compiler is not needed any more. This is **ahead-of-time** (AOT) compilation. Go works this way. In the cookbook picture, the whole book is translated before the cook opens it.

**Interpreting.** An **interpreter** is a program that reads instructions and carries them out one at a time, while the program runs, without producing a machine-code file. It is a translator who stands next to the cook and reads each line aloud as the cooking happens. It starts fast and is flexible, but the translating never stops, so the cooking is slower.[^pyglossary]

**Bytecode and a virtual machine.** Most popular languages today mix the two. A compiler does the first steps and writes **bytecode**: instructions for an imaginary, simplified processor, designed so that any real computer can run them. A program called a **virtual machine** (VM) then runs that bytecode on the real chip. Java's VM goes one step further. It watches which parts run most often, the "hot" parts, and compiles those into real machine code while the program is running. That is called **just-in-time** (JIT) compilation.[^javaman] Back in the kitchen, the recipe is written in a shorthand every local helper can read, and when the helper notices the same sauce being made every day, they write out a full translation of that one page.

<ThreeRoutes />

**In one line:** translate everything first, translate as you go, or translate halfway and finish on each machine.

## The same program three ways

Here is the price-with-tax program in all three languages, built and run on one laptop: OpenJDK 25, Python 3.10 and Go 1.27. Each one prints `220`.

### Java: bytecode, then a virtual machine

```java
public class Tax {
    static int total(int price, int rate) {
        return price + price * rate / 100;
    }

    public static void main(String[] args) {
        System.out.println(total(200, 10));
    }
}
```

`javac Tax.java` compiles it into `Tax.class`, a file of Java bytecode, 456 bytes long.[^javac] The command `javap -c` shows what is inside, in readable form:[^javap]

```text
$ javap -c Tax.class
  static int total(int, int);
    Code:
       0: iload_0
       1: iload_0
       2: iload_1
       3: imul
       4: bipush        100
       6: idiv
       7: iadd
       8: ireturn
```

Eight instructions. `iload` puts a number on a pile (a "stack"), `imul` multiplies the top two, `idiv` divides, `iadd` adds, `ireturn` hands back the answer.[^jvms6] Notice that this is still not Intel or ARM code. The Java specification says it plainly: the Java Virtual Machine "knows nothing of the Java programming language, only of a particular binary format, the class file format".[^jvms1] The same `Tax.class` runs on any computer that has a Java VM.

To watch the JIT at work, I called `total` a million times in a loop and asked Java to report what it compiles:[^javaman]

```text
$ java -XX:+PrintCompilation TaxLoop
13    8       3       TaxLoop::total (9 bytes)
13    9       4       TaxLoop::total (9 bytes)
…
```

Early in the run, the VM compiled `total`, all 9 bytes of its bytecode, first with a quick compiler (level 3) and then with its strongest optimizer (level 4). Java calls this tiered compilation: a fast first version, then a better one for the code that stays busy.[^tiered]

### Python: bytecode, then an interpreter

```python
def total(price, rate):
    return price + price * rate // 100

print(total(200, 10))
```

Python is often called "interpreted", but it compiles too. The official glossary says so: "Python source code is compiled into bytecode", and that bytecode is cached in `.pyc` files so the next start is faster.[^pyglossary] Compiled into such a file, this program's bytecode takes 254 bytes. The `dis` module shows the bytecode:[^dis]

```text
  2   0 LOAD_FAST        0 (price)
      2 LOAD_FAST        0 (price)
      4 LOAD_FAST        1 (rate)
      6 BINARY_MULTIPLY
      8 LOAD_CONST       1 (100)
     10 BINARY_FLOOR_DIVIDE
     12 BINARY_ADD
     14 RETURN_VALUE
```

Eight instructions again, and almost the same ones as Java: load, load, load, multiply, load 100, divide, add, return. The difference is what happens next. In Python 3.10 the interpreter carries out these instructions one by one, every time, and never turns them into machine code. Newer versions of Python have started experimenting with a JIT of their own.[^pep744]

### Go: machine code, ahead of time

```text
$ go build -o tax tax.go
$ ls -l tax
-rwxrwxr-x 1 danielbaumann danielbaumann 2346857 out 26 23:29 tax
$ file tax
tax: ELF 64-bit LSB executable, x86-64, … statically linked, …
$ ./tax
220
```

`go build` runs every step at once and writes `tax`, a file of real Intel machine code.[^gobuild] It is 2.3 MB for a program that prints one number, because Go copies everything the program needs into that one file, including the Go runtime, its built-in helper code. Go's documentation calls this "statically-linked" and explains the size the same way.[^gofaq] The good side: you can copy that single file to another Linux computer with the same kind of chip and run it, with nothing else installed.

The flag `-gcflags=-S` asks the compiler to print the machine code it wrote, in readable form, called assembly (addresses and file names trimmed):[^gocmd]

```text
main.total STEXT nosplit size=45 …
  IMULQ  AX, BX
  MOVQ   BX, CX
  SARQ   $63, BX
  MOVQ   AX, DX
  MOVQ   $-6640827866535438581, AX
  …
  SARQ   $6, CX
  SUBQ   BX, CX
  LEAQ   (CX)(SI*1), AX
  RET
```

Twelve instructions and 45 bytes. That giant negative number is the trick from step 5: it replaces "divide by 100" with a multiply and a shift (`SARQ`).[^granlund] And in `main`, the compiler skipped the call entirely. It worked out the answer while building, and the machine code just says `MOVL $220, AX`: put 220 in a slot, then print it. Asking for the compiler's decisions with `-gcflags=-m` confirms it: "inlining call to total".[^gocmd]

**In one line:** Java and Python both make bytecode; Java's VM compiles the busy parts at run time, Python 3.10 interprets, and Go hands over finished machine code.

## Errors: caught early or caught late

The meaning check in step 3 is where many mistakes are caught. I made the same mistake in all three programs: passing the price as text, `"200"` (in quotes), instead of the number 200.

Java and Go refuse to build at all:[^jls][^gospec]

```text
$ javac Tax.java
Tax.java:7: error: incompatible types: String cannot be converted to int
$ go build -o tax tax.go
./tax.go:10:20: cannot use "200" (untyped string constant) as int value in argument to total
```

No program file is produced, so the mistake cannot reach anyone. Python checks types only when the line actually runs. My broken Python program printed "Starting..." first, and failed only when it reached the bad line:

```text
Starting...
Traceback (most recent call last):
  …
TypeError: unsupported operand type(s) for //: 'str' and 'int'
```

Neither approach is simply better. Checking early catches whole families of mistakes before a program reaches you. Checking late lets programmers try ideas quickly, without writing out every type. But if you have ever seen an app crash on one particular screen, you have met an error that nothing caught early.

**In one line:** a compiler that checks types turns some crashes into error messages for the programmer instead.

## Why it matters to you

You will probably never run a compiler. Its work still shows up in your day.

- **Speed.** Optimized machine code does the same work with fewer, cheaper instructions, like the division trick above. The JIT is why a long-running Java program speeds up after it starts.[^tiered]
- **Errors caught early.** Every mistake a compiler refuses is one that never reaches your screen.
- **One program, many machines.** Bytecode lets one Java file run on any computer that has a Java VM, whatever its chip.[^jvms1] Go goes the other way: it can build a separate machine-code file for each kind of computer, chosen with two settings, `GOOS` for the operating system and `GOARCH` for the chip.[^goenv]
- **Memory.** Bringing a helper costs something. On my laptop, the tiny Java program needed about 41 MB of memory while running, the Python one about 8.6 MB, and the Go one under 2 MB. The VM and the interpreter come along for the ride.

## What my video pipeline taught me

I make videos with code: a small program draws every frame, and I described the whole pipeline in [issue 4, Videos drawn with code](/04-videos-drawn-with-code/). Writing this post, I realised that pipeline is shaped like a compiler.

<VideoCompiler />

The **source code** is `storyboard.json`, a text file that lists every scene with its text and how long it lasts. A checking step, `lint:blueprint`, reads it before anything is drawn and refuses a bad one, the way a type checker does: a topic title longer than three words, or the parts of the video in the wrong order, stops the build with an error.[^dr4w] Next, a timeline gives every scene its exact start frame, an **in-between form** that is easier to work with than the storyboard. Then comes **code generation**: one function per scene, `render(t)`, which takes a time and draws the picture for that moment. Finally FFmpeg, a standard video tool, encodes the pictures into small video pieces and joins them into one file, much like a linker joins compiled pieces, called object files, into one program.[^gocmd]

Two compiler ideas turned out to matter most.

**Only rebuild what changed.** Large programs are compiled in pieces, and only the pieces that changed are compiled again; this is called **incremental compilation**. Go, for one, keeps a cache of earlier build results and reuses them.[^gocache] My pipeline does the same. Each scene gets a fingerprint, a hash, of its storyboard entry, its drawing code, the engine, the fonts and the style. If the fingerprint has not changed, the finished video pieces are reused. Fixing one scene redraws only that scene.[^dr4w]

**The same input must give the same output.** A compiler that produced a different program every time would be impossible to trust. For the same reason, `render(t)` is not allowed to read the clock or use real randomness, and one of my automatic checks draws the same frames in two separate browser sessions, one walking backwards, and compares the pixels.[^dr4w] Without that rule, the reuse above would be unsafe: a reused piece must look exactly like a fresh one.

**In one line:** anything that turns a description into a result, step by step, ends up looking like a compiler.

## Recap

- Source code is text written by people; a processor only runs machine code, tiny numbered instructions.
- A compiler translates in fixed steps: tokens, tree, meaning check, in-between form, optimizing, code generation.
- Go compiles ahead of time into one machine-code file; the compiler is not needed to run it.
- Java compiles to bytecode, and its virtual machine compiles the busy parts to machine code while running (JIT).
- Python compiles to bytecode too, and in version 3.10 interprets it one instruction at a time.
- Compilers that check types turn some crashes into error messages before you ever see the program.
- The same ideas work outside programming: check the input early, rebuild only what changed, and keep the output repeatable.

| Word | Meaning |
| --- | --- |
| Source code | Instructions written by a person as text |
| Machine code | Instructions a processor runs directly |
| Compiler | A program that translates source code before it runs |
| Interpreter | A program that carries out instructions one at a time while the program runs |
| Bytecode | Instructions for an imaginary processor, run by a virtual machine |
| JIT | Compiling the busy parts to machine code while the program runs |
| Type | The kind of value a name holds, such as a whole number or text |
